### Assistant Response 1

      Read all three. Most of the audit holds. One point is framed wrong, and it
                    missed three things — one worse than anything on its list.

## Where the audit is right

   **(5) missing `set -e`** — real, and the cascade is worse than "proceeds to
       make install." After a failed install, `initialize_database` runs `mysqld
 --initialize-insecure`. If `make install` wrote nothing, that fails loudly. The
     quiet version is a *partial* install: an older `mysqld` from a previous run
      still sitting in `installed-files/bin/`, now initializing a data directory
                        against binaries that don't match the source just built.

  **(2) no preflight** — confirmed. `-DWITH_SSL=system` needs OpenSSL headers,
  MySQL's parser generation needs bison, ccache 4.x mandates libzstd (the script
    comments on this and then leaves cmake to complain). This machine has all of
                                              them, so the gap never shows here.

                                       **(3) and (4)** — confirmed as written.

     **(6) the scrape** — the PCRE half doesn't apply here: your grep is ugrep
7.8.4 built with pcre2jit, so `-oP` works. The real failure mode is that nothing
   checks the result. Empty version → comparison against installed can't match
   → URL becomes `.../MySQL-/mysql-.tar.gz` → wget fails → no `set -e` →
   cmake runs against a source tree that `download_and_extract` just `rm -rf`'d.
                                   Same bug as (5), reached by a different road.

**Threads** — concrete on this box: 14 cores, 31 GB, ~4 in use. `make -j14` on
   MySQL at roughly 2 GB per translation unit is 28 GB against 27 free. It fits,
                                                             barely, then swaps.

## Where I'd reframe point 1

 Hard-coding the directory isn't the defect — it's your house rule: hard-coded
     path at the top, *plus* an argument to override it. boost and ccache do the
  first half only. But so do `install`, `compile`, `update`, and `dbimport`. The
           three that *do* take a directory as first argument are `start-mysql`,
`mysql-client`, and `mysql-install`. This is a split convention across the whole
                                  scripts directory, not a boost/ccache failing.

      Where it actually bites today: `compile` self-bootstraps ccache by calling
`${DIR}/scripts/ccache` with no argument, so whatever directory compile was told
        about is silently dropped and ccache builds into its own hard-coded one.

## Three the audit missed

   **1. mysql-install eats its own version argument.** Its header promises "uses
 specified version." The directory parser claims any first argument not starting
 with `--`, so `./scripts/mysql-install 8.4.0` sets the project directory to the
literal string `8.4.0`, shifts it away, finds no version argument remaining, and
               scrapes the newest release instead — then builds a junk tree at
  `./8.4.0/mysql/` relative to wherever you were standing. Silent, and it writes
    to disk. Separately, `DIR="$1"` is never made absolute, so even a legitimate
   relative directory argument only works from one starting point, which defeats
                        the run-from-anywhere rule the argument exists to serve.

   **2. The closing instructions name a script that doesn't exist.** Step 1 says
run `${DIR}/scripts/mysql-start`. The file is `scripts/start-mysql`. That rename
     is what your issue 121 proposes and it hasn't been done — the message was
written against the intended name. It's the first thing a new person types after
                                                              a 40-minute build.

              **3. MySQL fetches a second Boost mid-build.** `-DDOWNLOAD_BOOST=1
      -DWITH_BOOST="${MYSQL_DIR}/boost"` tells MySQL's cmake to download its own
        pinned Boost into `mysql/boost/`, entirely separate from the 1.81.0 that
`scripts/boost` builds into `libs/boost/` for the server. So "builds from source
into project-local directories" has an undeclared network fetch inside it, and a
  version disagreement there fails deep in cmake — the exact confusing-failure
                                                         class point 2 is about.

      Related, while I was in there: `compile` sets `BOOST_VERSION="1.74.0"` and
    `BOOST_VERSION_UNDERSCORE="1_74_0"` at the top and never reads either — it
   passes `BOOST_ROOT` at the directory and lets cmake discover the version. The
   installed headers say 1.81. Two dead constants that will tell the next reader
                                                                the wrong thing.

## What I'd change, in order

 1. `set -e` in mysql-install, and check the scraped version is non-empty before
                                                                       using it.
   2. Fix the argument collision — a `--dir` flag, or require the version as a
                                       named flag, so the two can't be confused.
      3. Add the preflight: compiler, cmake, bison, OpenSSL and ncurses headers,
           libzstd, `file`, and whichever of curl/wget each script actually uses
    (they're inconsistent — boost and ccache use curl, mysql-install uses wget
                                                        with `--show-progress`).
       4. Give boost and ccache the directory argument, and have compile pass it
                                                                        through.
                         5. Cap MySQL's job count by RAM rather than core count.
     6. Fix the `mysql-start` reference, and either finish the root-password and
                     database-creation steps or say plainly that they're manual.
                              7. Delete the two dead Boost constants in compile.

  Want me to do these? And on 6 — should mysql-install set a root password and
 create the AzerothCore databases itself, or is stopping at an insecure init the
                             intent, with the credential script owning the rest?
