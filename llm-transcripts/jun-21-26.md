## The pruning pass I added


It runs on every upstream update, **after** cloning the new version but
**before** applying patches. For each patch, against the pristine new tree, it
returns one of four verdicts:


1. **RETIRE (convergence)** — the patch's own `needs_applying` probe says it's
no longer needed: upstream adopted your shape. Delete the patch.

2. **STALE (disappearance)** — the anchor pattern is gone entirely: upstream
restructured the code. Re-target or drop.

3. **REVIEW (collision)** — upstream's changed line ranges (parsed from `git
diff --unified=0 OLD NEW` hunk headers) overlap the patch's anchor line. The
patch may still *apply* but no longer *mean* the same thing. Flag it.

4. **OK** — anchor intact, region untouched.


The tagged-comment mechanism you asked for: on COLLISION/STALE it sed-inserts a
uniquely-tagged line above the anchor, in the file's own comment syntax —
`[[PATCH-AUDIT <id> <OLD>..<NEW>]] upstream changed this region — confirm...
then remove this line.` One `grep -rn PATCH-AUDIT` then enumerates every site
any agent or human must decide on; the tag *is* the worklist. Two lifetimes: the
in-tree tags are ephemeral (they vanish on the next disposable-tree reset,
perfect for one review session), and a persistent `audit-<NEW_REF>.md` report
keeps the durable record. It's wired to `.upstream-lock`, which stores the last
*successfully-built* upstream commit so the audit always compares against a
known-good baseline.


## The pitfalls, described


These are the failure modes the prose now spells out (no scaffold needed):


- **Never `unapply` defensively.** Unapply matches the *post-patch shape* and can't tell "we did this" from "upstream now ships this" — so on a converged upstream it reverts clean code into phantom dirt that looks like an upstream regression. Use `git reset --hard` for any cleanup where you don't *know* the patch is yours. Most expensive mistake.

- **Anchor every pattern to exactly one site.** Verify with `grep -c`; a count of 0 or >1 is a bug. Unanchored patterns silently corrupt a second match.

- **Wrap multi-line inserts in unique markers.** Reverting by re-matching content is fragile when upstream reflows around you; a marker is a stable handle, and it doubles as the audit witness.

- **Idempotency is mandatory.** Retries, re-sourcing, and trap-on-top-of-explicit-revert all run things twice. Guard apply on "unpatched present?" and unapply on "patched present?"

- **Test the round-trip, not just the apply.** Acceptance = `apply → build → unapply → git diff empty`. A patch that doesn't reverse cleanly leaks dirt into the *next* build, where it's much harder to trace.

- **Trap + hard-reset cover disjoint failures.** The EXIT trap handles normal failure but not SIGKILL/OOM/power loss; the unconditional pre-flight reset is the backstop for those. Keep both.

- **A patch that stops matching is the system working.** Re-target that one patch; don't pin upstream or fork. The loud failure is the feature.

- **Run the pruning pass or the set rots** — redundant/stale/silently-drifted patches accumulate invisibly otherwise.

- **Runtime-tuning after the validation gate** so a bad knob can't masquerade as a build failure.

- **Record the upstream ref only on success**, or a failed update poisons the audit baseline.

- **Never commit the source tree; treat any surviving edit as a bug** — the whole guarantee rests on `upstream + patches` being the only source of the result.

## Why each decision


- **Forward-only, no unapply.** The local build reverts so the source stays pristine; the contribution *wants* the diff to land in a commit. Same function, opposite downstream handling — a clean conceptual mirror of the existing system.

- **One patch → one PR.** This falls straight out of the one-to-one targeting principle. Each patch is already a single, named, anchored, self-justified change — exactly the shape reviewers want. A multi-patch PR would defeat that.

- **Eligibility gate (`UPSTREAMABLE` header field).** Some patches are genuine upstream value (bug fixes, warning fixes, hooks); others are local opinions that would break other users. Add a header line per patch — `UPSTREAMABLE: yes (behind config flag FOO)` or `no (local behavior change)`. Behavior changes that *are* upstreamable should go behind a config flag upstream so existing installs are unaffected, and the prose "patch doc" is what you hand reviewers as the PR body.

- **Verify-match before anything outward.** Reuses the audit pass's collision logic: if the anchor no longer matches HEAD, you'd be opening a PR against stale assumptions. Abort loudly instead.

- **tmp/ handling per your convention.** Working clone goes in the RAM-backed `tmp/` symlink, shallow to keep it small, with a size pre-check that aborts if it won't fit; explicitly `rm`'d at the end. The *fork* (server-side, on the GitHub account) persists unless separately deleted — that's its own approval.

- **Manual approval is structural, not advisory.** The pipeline *prepares* everything and stops at step 8 with the diff and PR body rendered. Every outward action — fork, push, PR open, fork delete — is individually gated on an explicit yes. Nothing reaches the network without one. (This matches how I'd treat any publishing action anyway.)

## What the reframe changed


The guiding shift is stated up front in a new **"Principle: machinery, not
procedure"** section: every "remember to…" is a defect, to be converted into
one of four mechanical forms — a **guard**, a **trap**, a **generated
artifact**, or a **gate** — and only three irreducible inputs are left to a
human (the transformation text + anchor, the upstreamability judgment, the
approval of an outward action). Everything else is wired.


Concretely, the procedural sections became machinery descriptions:


- **The "walk the path" step list → a build driver as a wired pipeline.** Each line of the composition is annotated with the *precondition it guarantees for the next edge* (`reset ⟶ source==HEAD`, `trap ⟶ revert no matter what`, `lock write ⟶ baseline advances only on success`). Nobody performs steps; the driver runs the graph.


- **The "add a patch" checklist → a generator + a verifier + a generated registry.** `scaffold-patch` stamps the component, `verify-patches` is an assertion harness (round-trip exactness, match-count vs the declared `MATCHES` field, witness present/absent) wired as a build gate so a broken patch *can't* enter the set, and `gen-registry` recomputes the registry from headers so it can't drift. The forgettable manual steps cease to exist as manual acts.


- **The de-patching "which do I use?" table → "each mechanism wired to its own trigger; the call site selects, not the operator."** The convergence-bug rationale now explains *why the wiring is split that way* rather than asking the reader to choose correctly.


- **The pruning "pass you run" → a machine invoked by the update path so it can't be skipped**, computing verdicts and emitting its own worklist (auto-inserted tags) plus a durable report.


- **The contribution "pipeline" of numbered steps → a driver-as-graph with explicit GATEs** at the outward edges, with forge detection *computed* from the remote and the clone-placement decision *measured* (current free space, logged fallback).


- **The pitfalls list → "Failure modes the machinery is built to foreclose,"** each stated as *the bug + the part that makes it impossible*, rather than advice to follow.


The patch anatomy also gained header fields (`ANCHOR`, `WITNESS`, `MATCHES`)
that are no longer prose decoration — they're the data the generator emits and
the verifier and audit machine read back, which is what lets those tools be
deterministic instead of interpretive.
