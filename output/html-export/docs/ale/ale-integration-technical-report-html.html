Overview

This document traces the complete data flow and control handoff between AzerothCore (C++), the Azeroth Lua Engine (ALE), and our custom Lua scripts. Focus is on the boundary points where control and data cross between systems.

Part 1: Server-Side Event Generation

1.1 World Update Loop

AzerothCore's main game loop runs in World::Update(). Each tick processes: - Player movement - Creature AI - Spell effects - Network packets

Events originate from these subsystems and propagate to ALE hooks.

1.2 Event Trigger Points

Events are generated at specific C++ locations. Key examples:

| Event | Source Location | Trigger Condition | |--------------------------|------------------------------------------|------------------------------| | PLAYER_EVENT_ON_LOGIN | WorldSession::HandlePlayerLogin | Player enters world | | PLAYER_EVENT_ON_LOGOUT | WorldSession::LogoutPlayer | Player leaves world | | PLAYER_EVENT_ON_KILL | Unit::Kill | Unit dies to player damage | | CREATURE_EVENT_ON_SPAWN | Creature::InitEntry | Creature spawns | | GAMEOBJECT_EVENT_ON_USE | Spell::EffectOpenLock | Player uses gameobject |

1.3 Hook Dispatch Entry

Each event location calls an ALE hook function. The call site pattern:

``cpp // In AzerothCore source (e.g., WorldSession.cpp) void WorldSession::HandlePlayerLogin(/ ... /) { // ... player initialization ...

// Hook call - control transfers to ALE sALE->OnLogin(player); // <-- BOUNDARY CROSSING

// ... continue player setup ... } 


Critical Files:
- WorldSession.cpp - Player login/logout
- Unit.cpp - Combat events
- Creature.cpp - Creature AI events
- GameObject.cpp - Interaction events

<h2>Part 2: ALE Engine Internals</h2>


<h3>2.1 The Lua State</h3>


ALE maintains a single lua_State L throughout the server&#39;s lifetime. This state contains:
┌─────────────────────────────────────────────────────────────────┐ │ LUA STATE │ ├─────────────────────────────────────────────────────────────────┤ │ REGISTRY (LUA_REGISTRYINDEX) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ [1] = function (callback for event A) │ │ │ │ [2] = function (callback for event B) │ │ │ │ [3] = table (instance data for map 0) │ │ │ │ [4] = function (timed event callback) │ │ │ │ ... = mixed (refs allocated/freed dynamically) │ │ │ │ ["Player"] = metatable for Player userdata │ │ │ │ ["Creature"] = metatable for Creature userdata │ │ │ │ ["GameObject"] = metatable for GameObject userdata │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ GLOBALS (_G) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ Player = metatable (same as registry) │ │ │ │ Creature = metatable (same as registry) │ │ │ │ RegisterPlayerEvent = C function │ │ │ │ GetPlayersInWorld = C function │ │ │ │ ... user scripts populate this ... │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ STACK (temporary, per-call) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ [top] = current operation values │ │ │ │ [...] = function arguments, return values │ │ │ │ [1] = bottom of stack │ │ │ └────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────┘ 

<h3>2.2 Hook Handler Functions</h3>


Each event type has a handler in ServerHooks.cpp or PlayerHooks.cpp:
cpp // mod-ale/src/LuaEngine/hooks/PlayerHooks.cpp void ALE::OnLogin(Player player) { START_HOOK(PLAYER_EVENT_ON_LOGIN); // Macro: sets up event key Push(player); // Push userdata to Lua stack CallAllFunctions(PlayerEventBindings, key); // Execute all registered callbacks } 

START_HOOK macro expansion:
cpp #define START_HOOK(EVENT) \ LOCK_ALE; \ // Acquire mutex if (!ALEConfig::GetInstance().IsALEEnabled()) return; \ // Check enabled auto key = EventKey<Hooks::PlayerEvents>((Hooks::PlayerEvents)EVENT);

// LOCK_ALE is a RAII guard: struct ALELock { ALELock() { sALE->mutex.lock(); } ~ALELock() { sALE->mutex.unlock(); } }; #define LOCK_ALE ALELock _aleLock 


The lock ensures single-threaded access to the Lua state. All hook handlers acquire this lock before touching any Lua data.


<h3>2.3 Data Transformation: C++ to Lua</h3>


The Push() family of functions converts C++ types to Lua values:


| C++ Type         | Lua Type      | Push Function                    |
|------------------|---------------|----------------------------------|
| Player        | userdata      | Push(L, player) → metatable    |
| Creature      | userdata      | Push(L, creature) → metatable  |
| uint32         | number        | Push(L, value) → lua_pushint   |
| std::string    | string        | Push(L, str) → lua_pushstring  |
| ObjectGuid     | number        | Push(L, guid) → uint64         |
| bool           | boolean       | Push(L, val) → lua_pushboolean |


Userdata wrapping (LuaFunctions.cpp):
cpp template <typename T> void ALE::Push(lua_State L, T const obj) { if (!obj) { lua_pushnil(L); return; }

// Create userdata containing pointer (T)lua_newuserdata(L, sizeof(T)) = const_cast<T>(obj);

// Attach metatable for type checking and method dispatch lua_pushstring(L, ALE::GName<T>()); // Type name: "Player", "Creature", etc. lua_rawget(L, LUA_REGISTRYINDEX); // Get metatable from registry lua_setmetatable(L, -2); // Attach to userdata } 


Memory layout of userdata:
┌─────────────────────────────────────────────────────────────────┐ │ LUA USERDATA (on Lua heap) │ ├─────────────────────────────────────────────────────────────────┤ │ Header: GC info, type tag, size │ │ Data: [ Player pointer ] ← 8 bytes, points to C++ object │ │ Meta: → "Player" metatable in registry │ └─────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────┐ │ C++ PLAYER OBJECT (server heap) │ ├─────────────────────────────────────────────────────────────────┤ │ Unit base class fields... │ │ Player-specific fields... │ │ m_name, m_level, m_position, etc. │ │ ALEEvents ALEEvents; ← Pointer to timed event processor │ └─────────────────────────────────────────────────────────────────┘ 

The userdata is a thin wrapper. Lua owns the userdata memory (8 bytes for a pointer).
The server owns the actual Player object. When the Player is deleted in C++, the userdata
becomes a dangling pointer. ALE handles this via InvalidateObjects() after callbacks.


<h3>2.4 Metatable System</h3>


Each C++ type has a metatable registered in the Lua registry. Metatables enable:
- Method dispatch (player:GetName() → PlayerMethods::GetName)
- Type checking (luaL_checkudata verifies metatable matches)
- Operator overloading (comparison, arithmetic if needed)


Metatable structure:
<pre><code class="lua"><span class="comment">-- Registry[&amp;quot;Player&amp;quot;] contains:</span>
{
    __index = {
        GetName = &amp;lt;C <span class="keyword">function</span>: PlayerMethods::GetName&amp;gt;,
        GetLevel = &amp;lt;C <span class="keyword">function</span>: PlayerMethods::GetLevel&amp;gt;,
        GetGUID = &amp;lt;C <span class="keyword">function</span>: WorldObjectMethods::GetGUID&amp;gt;,
        RegisterEvent = &amp;lt;C <span class="keyword">function</span>: WorldObjectMethods::RegisterEvent&amp;gt;,
        <span class="comment">-- ... hundreds of methods ...</span>
    },
    __tostring = &amp;lt;C <span class="keyword">function</span>: prints &amp;quot;Player: &amp;lt;name&amp;gt;&amp;quot;&amp;gt;,
    __eq = &amp;lt;C <span class="keyword">function</span>: compares GUIDs&amp;gt;,
}</code></pre>


Method dispatch flow:
Lua: player:GetLevel() │ ▼ Lua VM: getfield(player, "GetLevel") │ player has no "GetLevel" field │ Check metatable.__index ▼ Metatable.__index["GetLevel"] → C function pointer │ ▼ C call: PlayerMethods::GetLevel(L, player) │ │ // Extract Player from userdata │ Player player = CHECKOBJ<Player>(L, 1); │ │ // Call actual C++ method │ uint8 level = player->GetLevel(); │ │ // Push result to Lua stack │ Push(L, level); │ ▼ Returns 1 (one value on stack) 

<h3>2.5 Registry and Binding Maps</h3>


ALE stores callback references in multiple binding maps:
cpp // LuaEngine.h BindingMap<EventKey<PlayerEvents>> PlayerEventBindings; // RegisterPlayerEvent BindingMap<EventKey<ServerEvents>> ServerEventBindings; // RegisterServerEvent BindingMap<EntryKey<CreatureEvents>> CreatureEventBindings; // RegisterCreatureEvent // ... etc 

The Lua Registry as Memory Pool:


The Lua registry is a special table at pseudo-index LUA_REGISTRYINDEX. Unlike normal tables,
it uses integer keys allocated by luaL_ref():
Registry Slot Allocation: ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐ │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │ ... │ ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤ │func │func │tbl │FREE │func │FREE │func │tbl │ │ │(ev) │(ev) │(dat)│ │(tim)│ │(ev) │(dat)│ │ └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘ ↑ ↑ ↑ │ │ └── Freed slot, available for reuse │ └── Instance data table └── Event callback function

luaL_ref(L, LUA_REGISTRYINDEX): 1. Pop value from stack 2. Find first free slot (linked list of freed slots) 3. Store value in slot 4. Return slot number (the "ref")

luaL_unref(L, LUA_REGISTRYINDEX, ref): 1. Set registry[ref] = nil 2. Add ref to free list 3. Slot now available for next luaL_ref() 


Registration flow:
Lua: RegisterPlayerEvent(3, myCallback) │ ▼ GlobalMethods.h: RegisterEventHelper() │ luaL_checktype(L, 2, LUA_TFUNCTION) ← CRITICAL: Type check here │ lua_pushvalue(L, 2) ← Copy function to top of stack │ int funcRef = luaL_ref(L, LUA_REGISTRYINDEX) ← Pop and store, get ref ▼ LuaEngine.cpp: Register() │ key = EventKey<PlayerEvents>(PLAYER_EVENT_ON_LOGIN) │ PlayerEventBindings->Insert(key, funcRef, shots) ← Store binding ▼ BindingMap.h: Insert() │ uint64 id = ++next_id │ Binding b = new Binding(L, id, funcRef, shots) │ bindings[key].push_back(unique_ptr<Binding>(b)) │ id_lookup_table[id] = iterator_to_binding ▼ createCancelCallback(L, id, bindings) ← Returns closure that can remove binding 

Binding ownership model:
┌─────────────────────────────────────────────────────────────────┐ │ BindingMap │ ├─────────────────────────────────────────────────────────────────┤ │ bindings: map<EventKey, list<unique_ptr<Binding>>> │ │ │ │ │ ▼ │ │ ┌──────────────┐ │ │ │ Binding │ │ │ ├──────────────┤ │ │ │ funcRef: 5 │───┐ │ │ │ shots: 0 │ │ │ │ │ id: 12345 │ │ │ │ └──────────────┘ │ │ │ │ │ │ ▼ │ │ ┌────────────────┐ │ │ │ Lua Registry │ │ │ │ [5] = func │ │ │ └────────────────┘ │ │ │ │ When Binding is destroyed (unique_ptr deleted): │ │ ~Binding() { luaL_unref(L, LUA_REGISTRYINDEX, funcRef); } │ │ │ │ This frees registry slot 5 for reuse. │ └─────────────────────────────────────────────────────────────────┘

ExecuteCall (actually runs the Lua function):
cpp // LuaEngine.cpp:844 bool ALE::ExecuteCall(int params, int res) { int base = lua_gettop(L) - params;

Separate from global event bindings, timed events attach to specific WorldObjects:

<h2>Part 5: Registry Corruption Analysis (Issue 332)</h2>


<h3>5.1 Crash Point</h3>
cpp // LuaEngine.cpp:853 if (!lua_isfunction(L, base)) { ALE_LOG_ERROR("[ALE]: Cannot execute call: registered value is {}, not a function.", luaL_tolstring(L, base, NULL)); ASSERT(false); // "stack probably corrupt" } 

<h3>5.2 Data Flow to Crash</h3>
Normal flow: Event triggers → PushRefsFor() → lua_rawgeti(funcRef) → FUNCTION on stack → ExecuteCall

Corruption flow: Event triggers → PushRefsFor() → lua_rawgeti(funcRef) → TABLE on stack → CRASH ↑ funcRef points to wrong value 


The question: How does registry[funcRef] change from FUNCTION to TABLE?


<h3>5.3 Registry Slot Lifecycle</h3>
SCENARIO: Timed event re-registration pattern

Timeline: ┌────────────────────────────────────────────────────────────────────────────┐ │ T1: periodicEvent(func, 5000, 1, player) │ │ └─ luaL_ref() allocates slot 10, stores FUNCTION │ │ └─ LuaEvent created with funcRef=10 │ ├────────────────────────────────────────────────────────────────────────────┤ │ T2: 5 seconds later, event fires │ │ └─ ALEEventProcessor::Update() processes event │ │ └─ lua_rawgeti(L, REGISTRY, 10) → pushes FUNCTION │ │ └─ OnTimedEvent(10, ...) → calls ExecuteCall │ │ │ │ INSIDE the callback: │ │ └─ Lua: periodicEvent(func, 5000, 1, player) │ │ └─ luaL_ref() allocates slot 11, stores FUNCTION │ │ └─ New LuaEvent created with funcRef=11 │ │ └─ Callback returns │ │ │ │ AFTER callback: │ │ └─ RemoveEvent() called for original event │ │ └─ luaL_unref(10) frees slot 10 │ ├────────────────────────────────────────────────────────────────────────────┤ │ T3: Next iteration, new event fires... │ │ └─ Process repeats with funcRef=11 │ └────────────────────────────────────────────────────────────────────────────┘

This is CORRECT behavior. Slot 10 freed AFTER callback completes. 


<h3>5.4 Corruption Hypothesis: PushRefsFor Shot Depletion</h3>
cpp // BindingMap.h:194-210 void PushRefsFor(const K& key) { Guard guard(GetLock());

for (auto i = list.begin(); i != list.end();) { Binding& binding = i; auto i_prev = (i++);

// LINE A: Push function from registry lua_rawgeti(L, LUA_REGISTRYINDEX, binding.funcRef);

if (binding.remainingShots > 0) { binding.remainingShots--;

if (binding.remainingShots == 0) { // LINE B: Erase binding (destructor calls luaL_unref) list.erase(i_prev); // ← SLOT FREED HERE } } } } 


Potential issue: Between LINE A and LINE B:
1. Function is pushed to stack (safe, stack holds reference)
2. Binding destroyed, luaL_unref() frees registry slot
3. If lua_rawgeti is called AGAIN before lua_pcall...


But: The guard lock prevents concurrent access. And the function is already on stack.
So this should be safe.


<h3>5.5 Corruption Hypothesis: Instance Data Collision</h3>
Registry contains BOTH: - Event callback functions (from RegisterPlayerEvent) - Instance data tables (from CreateInstanceData)

They share the same integer namespace.

┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐ │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │ 9 │ ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤ │func │func │func │tbl │func │tbl │func │func │tbl │ │login│loot │timer│map0 │kill │map1 │chat │kill │map2 │ └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

If code MISTAKENLY uses an instance data ref as a funcRef: lua_rawgeti(L, REGISTRY, 4) → Gets TABLE (map0 data) ExecuteCall() → CRASH: not a function 


Storage locations:
- Event funcRefs: stored in Binding.functionReference
- Instance data refs: stored in instanceDataRefs[mapId] or continentDataRefs[instanceId]


These are separate data structures. Collision would require bug in ALE code.


<h3>5.6 Corruption Hypothesis: Threading Race</h3>
Thread A (World Update): Thread B (Map Thread): ───────────────────────────────── ───────────────────────────────── sALE->OnLogin(player) sALE->CreateInstanceData(map) │ │ LOCK_ALE LOCK_ALE (BLOCKED) │ │ PushRefsFor(key) │ │ │ lua_rawgeti(L, REG, 5) │ │ │ CallOneFunction() │ │ │ lua_pcall() │ │ │ [Lua callback runs] │ │ │ [callback returns] │ │ │ UNLOCK_ALE │ │ │ return LOCK_ALE acquired │ lua_istable(L, -1) luaL_ref() → gets slot N │ UNLOCK_ALE 

The LOCK_ALE ensures serialization. Thread B cannot touch registry while A is working.
But what if there&#39;s a path that DOESN&#39;T use LOCK_ALE?


<h3>5.7 Verified Safe Paths</h3>


All registration paths have type checking:
- luaL_checktype(L, 2, LUA_TFUNCTION) in GlobalMethods.h:597, 612, 629
- luaL_checktype(L, 2, LUA_TFUNCTION) in WorldObjectMethods.h:760


All hook handlers use LOCK_ALE:
- START_HOOK macro acquires lock
- OnTimedEvent explicitly calls LOCK_ALE


Conclusion: Corruption happens AFTER successful registration. The registry slot
is valid when created (type check passes), but somehow changes later.


<h3>5.8 Remaining Unknowns</h3>


1. Bytecode cache interaction - Was disabled, crash persists
2. Script reload timing - Does .reload ale leave dangling refs?
3. Object invalidation - InvalidateObjects() called after callbacks, could affect userdata
4. Extension load order - .ext files load before hooks ready (documented risk)

<h2>Part 7: Critical Boundary Summary</h2>


<h3>7.1 Lua Registry as Central Storage</h3>


All function references stored in single Lua registry:
- Global event callbacks (BindingMap)
- Timed event callbacks (ALEEventProcessor)
- Instance data tables (instanceDataRefs)
- Cancel callbacks (closures)


Registry slot lifecycle:
luaL_ref() → Allocates slot, stores value, returns int ref lua_rawgeti() → Retrieves value by ref luaL_unref() → Marks slot as free for reuse 

<h3>7.2 Thread Safety Boundaries</h3>


| Operation              | Lock Used           | Protected By                |
|------------------------|---------------------|-----------------------------|
| Binding map access     | BindingMap::GetLock | Guard in PushRefsFor        |
| Event processor update | LOCK_ALE            | Mutex in Update()           |
| Lua state access       | LOCK_ALE            | All hook functions          |
