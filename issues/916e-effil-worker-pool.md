# 916e - Effil Worker Pool

## Status
- Created: 2026-06-03
- Parent: Issue 916 (mod-soren-chat)
- Phase: 3
- Priority: High
- Depends on: 916c (effil-jit installed), 916d (the model runner to call)

## Overview

Spin up effil-jit worker threads on worldserver startup, one per
place-and-slot in `01-config.lua`'s `model_places` (for the three LAN
mini-PCs at three slots each, nine workers; for an in-server place at two
slots, two more). Each worker pops requests from shared inbox channels (step 2),
calls the model runner from 916d for its own place, and pushes results
onto a shared outbox channel. The main worldserver thread interacts
entirely via the two channels — never blocks on the model.

What a worker holds depends on its place (916d has the detail):

- **in-server:** its own llama.cpp context (its own key/value cache) made
  from the one model loaded at startup. Two in-server workers never share
  memory.
- **beside:** an address of one `llama-server` and one of that server's
  slots. Nine workers for three servers at `-np 3` keeps every slot busy.
- **in-client:** created when a W client offers its GPU, retired when
  that player logs out (custom-client issue 907). One worker per offering
  player. 916o's companion programs join the same way through its job
  broker.

Workers on players' machines (in-client, and 916o's companion programs)
are untrusted and take **chat requests only**. The request's `type`
field (`"guidance"` or `"chat"`) is what the pool routes on, so this
rule is one check at dispatch, not a convention (916o, step 1).

This is the load-bearing concurrency layer. Everything else in 916 is
"produce requests" or "consume responses" feeding into / out of this
pool.

## Current Behavior

No worker threads exist. effil-jit is installed (via 916c) but unused.

## Intended Behavior

After this sub-issue lands, the worldserver process has its additional
OS threads running. From the main thread's perspective, the workers are
two channels:

```lua
local workers = require("mod-soren-chat.workers")

-- Submit a request. Non-blocking — the call returns immediately.
-- request_id is generated by the worker pool and returned for matching.
local request_id = workers.submit({
    type       = "guidance",   -- or "chat"
    party_id   = 42,
    prompt     = "...",
    grammar    = GUIDANCE_GRAMMAR,  -- GBNF text from 916h, or nil
    max_tokens = 200,
    timeout_ms = 30000,
})

-- Drain any completed responses. Non-blocking — returns empty table
-- if nothing's ready. Called once per worldserver tick.
local responses = workers.drain()
```

Internally each worker runs an infinite loop: pop a request (blocking),
stop on the stop signal, otherwise call the model runner with its own
placement and `where`, and push `{ request_id, type, text, error,
tokens, millis, worker }` onto the outbox. `worker` is the place's name
and slot number (string, e.g. `"box2/1"`), so a reader of the logs sees
which place answered.

## Implementation Steps

1. Write `lua/03-effil-workers.lua`:
   - Read `model_places` from `01-config.lua`
   - Create three effil channels: the guidance inbox, the chat inbox, the outbox
   - For each place, spawn `slots` effil threads running the worker loop
   - Pass the placement, `where`, the place name and slot number, the
     channels, and a stop-signal sentinel as initial state to each thread
   - For in-server places: load the model once on the main thread first
     and pass its address as a number (916d explains why a number)
   - Expose `submit(request)` and `drain()` as the public API
   - Maintain a per-request_id counter for unique IDs
2. Dispatch: two shared inbox channels, one per request type —
   `guidance` and `chat`. Trusted workers pop from both (guidance first);
   workers on players' machines pop only from `chat`. Within one channel
   effil's blocking pop handles fairness, and a slow place simply takes
   fewer requests. (One shared channel would let an untrusted worker pop
   a guidance request, so the split is the trust rule made structural.)
   effil's pop takes a timeout, so a trusted worker checks `guidance`
   with a zero wait before blocking briefly on `chat`. (Per-worker inboxes come in 916f if
   health tracking wants targeted routing.)
3. On worldserver shutdown, push one stop signal per worker so each exits
   cleanly, then join, then free the in-server model.
4. Smoke test: submit 10 requests, drain until all come back, verify all
   completed and were spread across workers
5. Profile: worker startup time (in-server includes loading the model),
   channel push/pop latency, end-to-end request latency per placement

## Critical Notes on Effil

- Effil channels are thread-safe; both `:push` and `:pop` are atomic.
- Tables passed through channels are deep-copied (Lua values can't
  cross thread boundaries by reference — effil enforces this). This is
  fine for our small request/response payloads. `ffi` pointers cannot
  pass at all, which is why the in-server model's address travels as a
  number.
- Each effil thread starts with a fresh Lua state. They cannot share
  upvalues or globals with the main thread; everything must come
  through channels or initial-state args.
- Loading the model runner and dkjson inside the worker thread works
  because effil threads can `require()` their own copies. Each worker
  pays the load cost once at startup. For in-server workers that
  includes creating their context, which allocates their key/value cache.
- Worker crashes don't bring down the worldserver but do leak the
  request that was in flight. A crash *inside libllama* (in-server) is
  different: it is a crash of the whole process. 916d records that
  trade-off.

## Open Questions

- **Requests for one player's own machine.** 917c's plain-text commands
  steer bots, so they belong with guidance — except that a player's
  commands for their own bots may run on that same player's machine,
  because the player could have typed them (917c, "Where it may run").
  Two shared inboxes cannot express "this player's worker or a trusted
  one". Options: a small inbox per in-client worker that only its own
  player's requests go into, checked before the shared ones; or keep
  commands on trusted places only and give up the exception. Leaning
  the per-player inbox, which 916f's per-worker routing needs anyway.
- Per-worker inbox vs single shared inbox: shared is simpler and gives
  natural load balancing. Per-worker lets us route around an unhealthy
  worker. Lean toward shared in v0, add per-worker routing in 916f
  alongside health.
- Number of slots per beside place: three per mini-PC is a starting
  point; the benchmark decides (it trades per-reply speed for replies in
  flight).
- Number of in-server contexts: each costs a key/value cache's memory in
  the worldserver. Two is a starting point.
- Worker lifecycle: spawn once at startup vs lazy spawn on first
  request. Eager is simpler and the startup cost is small (except
  in-server model loading, which happens once either way). in-client
  workers are necessarily lazy.
