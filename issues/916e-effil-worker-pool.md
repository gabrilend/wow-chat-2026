# 916e - Effil Worker Pool

## Status
- Created: 2026-06-03
- Parent: Issue 916 (mod-soren-chat)
- Phase: 3
- Priority: High
- Depends on: 916c (effil-jit installed), 916d (ollama-client to call)

## Overview

Spin up three effil-jit worker threads on worldserver startup, one per
Ollama box. Each worker owns a request channel and pops requests from a
shared inbox channel, calls Ollama via the client from 916d, and pushes
results onto a shared outbox channel. The main worldserver thread
interacts entirely via the two channels — never blocks on HTTP.

This is the load-bearing concurrency layer. Everything else in 916 is
"produce requests" or "consume responses" feeding into / out of this
pool.

## Current Behavior

No worker threads exist. effil-jit is installed (via 916c) but unused.

## Intended Behavior

After this sub-issue lands, the worldserver process has three additional
OS threads running. From the main thread's perspective, the workers are
two channels:

```lua
local workers = require("mod-soren-chat.workers")

-- Submit a request. Non-blocking — the call returns immediately.
-- request_id is generated by the worker pool and returned for matching.
local request_id = workers.submit({
    type = "guidance",      -- or "chat"
    party_id = 42,
    prompt = "...",
    model = "llama3.2:1b",
    timeout_ms = 30000,
})

-- Drain any completed responses. Non-blocking — returns empty table
-- if nothing's ready. Called once per worldserver tick.
local responses = workers.drain()
for _, response in ipairs(responses) do
    if response.error then
        log.warn("request " .. response.request_id .. " failed: " .. response.error)
    else
        log.info("request " .. response.request_id .. " ok: " .. response.text)
        dispatch_to_handler(response)
    end
end
```

Internally each worker runs an infinite loop:

```lua
while true do
    local req = inbox:pop()  -- blocks until something arrives
    if req == STOP_SIGNAL then break end
    local resp, err = ollama_client.generate({
        url = my_box_url,
        model = req.model,
        prompt = req.prompt,
        timeout_ms = req.timeout_ms,
    })
    outbox:push({
        request_id = req.request_id,
        type = req.type,
        text = resp and resp.response,
        error = err,
        latency_ns = resp and resp.eval_duration,
        worker = my_box_name,
    })
end
```

## Implementation Steps

1. Write `lua/03-effil-workers.lua`:
   - Read config (host list) from `01-config.lua`
   - Create two effil channels: inbox and outbox
   - For each host, spawn an effil thread running the worker loop
   - Pass the host's URL, model name, channels, and a STOP_SIGNAL
     sentinel as initial state to each thread
   - Expose `submit(request)` and `drain()` as the public API
   - Maintain a per-request_id counter for unique IDs
2. Round-robin or queue-based dispatch: for v0 use a single shared
   inbox channel — all workers pop from the same channel, effil's
   blocking pop handles fairness. (Per-worker inboxes come in 916f if
   health tracking wants targeted routing.)
3. On worldserver shutdown, push STOP_SIGNAL three times so each worker
   exits cleanly, then join. Register the shutdown via ALE's
   `OnWorldUpdate` or equivalent.
4. Write a smoke test that submits 10 requests and drains until all
   come back, verifies all completed and were distributed roughly
   evenly across the three workers
5. Profile: measure worker startup time, channel push/pop latency, and
   end-to-end request latency

## Critical Notes on Effil

- Effil channels are thread-safe; both `:push` and `:pop` are atomic.
- Tables passed through channels are deep-copied (Lua values can't
  cross thread boundaries by reference — effil enforces this). This is
  fine for our small request/response payloads.
- Each effil thread starts with a fresh Lua state. They cannot share
  upvalues or globals with the main thread; everything must come
  through channels or initial-state args.
- Loading the ollama-client and dkjson modules inside the worker thread
  works because effil threads can `require()` their own copies. Each
  worker pays the load cost once at startup.
- Worker crashes don't bring down the worldserver but do leak the
  request that was in flight. Handle in 916f (health) — for v0 a
  worker crash is a bug to investigate, not a routine event.

## Open Questions

- Per-worker inbox vs single shared inbox: shared is simpler and gives
  natural load balancing. Per-worker lets us route around an unhealthy
  worker. Lean toward shared in v0, add per-worker routing in 916f
  alongside health.
- Number of workers: three (one per box). Could be 6 (two per box,
  matching NUM_PARALLEL=2 setups). Decision deferred to benchmark.
- Worker lifecycle: spawn once at startup vs lazy spawn on first
  request. Eager is simpler and the startup cost is small.
